# IT and cybersecurity role taxonomy

Map duties before titles. Select a primary family and relevant secondary families; hybrids are common. This is a practical editorial map, not an official workforce framework or a mandatory career ladder.

| Family | Evidence to surface | Calibration caution |
|---|---|---|
| Service desk / desktop support | Troubleshooting, ticket resolution, endpoint/account work, escalation quality, documentation | Service restoration and careful access handling are useful evidence without a cyber title |
| Systems administration | Windows/Linux, directory services, configuration, patching, automation, restores | Administration is not automatically security architecture |
| Network engineering | Routing/switching, DNS/DHCP, troubleshooting, segmentation, change validation | Firewall work is not proof of penetration testing |
| Endpoint / workplace engineering | MDM/UEM, deployment, application control, hardening, fleet health, exceptions | Coverage needs a defined eligible fleet and operating period |
| Cloud / platform / DevOps / SRE | IaC, CI/CD, observability, reliability, recovery, capacity/cost, incident learning | Separate cloud operations from security control design |
| IT management / architecture | Service ownership, delivery, roadmaps, vendors, reliability, budgets, team development | Show actual decision rights, not title-based headcount assumptions |
| SOC / security operations | Alert review, investigation, escalation, evidence handling, SIEM/EDR workflows | Alert volume alone is not detection effectiveness |
| Detection engineering | Telemetry selection, logic, test cases, tuning, deployment, validation | ATT&CK mapping is not demonstrated detection coverage |
| Incident response / DFIR | Timelines, containment, recovery, root cause, forensic artifacts, coordination | Distinguish responder, incident commander, and adviser |
| Threat intelligence | Collection requirements, source evaluation, analytical judgments, dissemination, decisions | IOC volume is not intelligence impact |
| Vulnerability / exposure management | Asset context, exploitability, prioritization, ownership, remediation validation, exceptions | Findings closed through decommissioning are not all patches applied |
| Cloud security | Identity guardrails, logging, posture, IaC controls, cloud incident handling | AWS/Azure/GCP are not interchangeable experience claims |
| Application / product security | Threat models, code review, SDLC controls, developer remediation, verification | Tool operation differs from engineering fixes or owning product risk |
| IAM / identity / PAM / IGA | Authentication, authorization, lifecycle, access reviews, privilege control, automation | Distinguish policy design, administration, and governance ownership |
| GRC / IT audit / risk | Control design/testing, evidence, risk decisions, audit response, policy implementation | Audit support differs from auditor responsibility or risk acceptance authority |
| Third-party risk | Vendor tiering, evidence evaluation, remediation, contract input, exceptions | Questionnaire counts alone do not show risk decisions |
| Penetration testing / red team | Authorized scope, attack paths, methods, constraints, findings, retests, defensive changes | Pentest, adversary emulation, and CTF/lab work are different contexts |
| Security engineering / architecture | Control integration, automation, design tradeoffs, platform reliability, adoption | “Zero trust” or product lists need concrete implementation evidence |
| Data / privacy security | Data flows, classification, access, encryption, retention, engineering controls | Privacy advice is not automatically legal authority |
| OT / ICS security | Asset visibility, monitoring, segmentation, vendor access, safety and uptime constraints | Do not transfer intrusive IT testing practices to OT by assumption |
| Security leadership / BISO / CISO | Strategy, operating model, talent, resources, risk decisions, executive communication | Identify actual organizational scope and accountability |
| Consulting / Field CISO / fractional CISO | Client problem, engagement contribution, adopted advice, delivery, commercial outcomes | Field CISO and fractional operational accountability differ |
| AI system security (when targeted) | Threat model, data/identity boundaries, evaluation method, tested controls, deployment context | Keep conventional security foundations; do not add AI claims for trend value |

## Level evidence

- **Early career:** sound foundations, supported tasks, troubleshooting, useful projects, clear learning and limits. No requirement for enterprise metrics.
- **Mid-level:** independent delivery, repeatable operations, improvements, concrete tools and constraints.
- **Senior / staff / principal IC:** complex problems, design judgment, reusable systems, mentoring and cross-team influence. People management is not required for seniority.
- **Manager / director:** team and program responsibility, priorities, coaching, resource decisions, sustained delivery. Explain direct vs indirect scope.
- **Executive:** breadth of accountable functions, governance, business tradeoffs, talent, resource allocation, crisis leadership. Technical expertise can remain a differentiator.

## Industry overlays

Healthcare may value clinical continuity and sensitive-data controls; financial services may value resilience and control evidence; federal/defense may require specific eligibility and workforce qualifications; SaaS may emphasize product trust and developer adoption; OT may prioritize safety and constrained maintenance. Apply an overlay only to candidate-stated experience or explicit target requirements. An employer name is not proof of HIPAA, FedRAMP, or any particular regulatory responsibility.
